# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Project discussion and docs live at the forum: https://www.depvana.com/topic/505

## Questions vs. instructions

Read requests literally:
- "Can you…", "is it possible…", "could you…", "would it work to…" are questions. Answer them (feasibility, approach, trade-offs) and don't change any code. Wait for an explicit go-ahead.
- "Do…", "make…", "change…", "go ahead", "implement…" are instructions. Implement them.

## Commands

There is no build step, linter, or npm script. Code is plain ES modules (`"type": "module"`) run directly by Node (v20) or the browser. There are no dependencies, not even dev ones.

```sh
node --test smep/tests/ smerp/tests/ webui/tests/   # all tests (node:test + node:assert/strict)
node --test smep/tests/protocol.test.js         # single file
node --test smerp/tests/unit/                   # one layer of tests (unit/ or integration/)
node --test --test-name-pattern="clamp" smep/tests/   # single test by name
node smerp/src/server/run-server.js             # mock relay on :8000
node playground/repl.js                         # REPL: 2 mock relays (:8001, :8002), clients alice/alice2/bob/carol
```

`playground/repl.js` imports `raven` and `raven/testing` by package self-reference, so it exercises the real `exports` map.

`smerp/src/storage/indexeddb/browser-test.html` exercises the IndexedDB storage in a browser.

## Architecture

A headless library: no UI ships with it. Two layers: `smerp` depends on `smep`; `smep` depends on nothing. Package entry points (`package.json` `exports`):
- `.` → `index.js`: the reference `SmerpClient` plus what a consumer needs to use it (identities, `EventTypes`, `ContentTypes`, storages, errors).
- `./smep` → `smep/src/index.js`: all primitives, for building a custom client.
- `./smerp` → `smerp/src/index.js`: client building blocks (storage/transport interfaces, sync, ingest, auth).
- `./testing` → `smerp/src/server/index.js`: mock relay. Uses `node:http`, so it must never be re-exported from `.` or `./smerp`.
- `./webui` → `webui/src/index.js`: browser UI (`WebUi`). Uses the DOM, so it must never be re-exported from `.` either.

Protocol specs (plain text, kept in sync with the code; the code is the source of truth): `smep/smep_rfc.txt` (envelope format, encryption), `smerp/smerp_rfc.txt` (relay upload/download, relay types, federation, client ntfy notifications), `smerp/src/auth/auth_rfc.txt` (GET auth).

Classes are checked with `instanceof` via `insist`, so every module must import identities from `smep`, never a copy.

**smep** is the pure crypto/envelope protocol with no I/O. It uses only WebCrypto (`crypto.subtle`), so the same code runs in Node and the browser.
- Identities are X25519 keypairs held as `CryptoKey`s (`PrivateIdentity` / `PublicIdentity`). Peers are addressed by the hex public key, called **pkh** throughout (`spkh`/`rpkh` = sender/recipient).
- `encrypt` / `createEnvelope`: X25519 ECDH → `sha256(shared_secret)` as key (`kdf.js`) → AES-GCM with random IV → binary envelope (keys, timestamp, content type, IV, ciphertext‖tag). Layout constants are in `envelope/layout.js`. `EnvelopeWriter` writes the 78-byte header first (`writeHeader` returns it as the AES-GCM AAD), then `writeBody`, then `finish`. Envelopes are at most 4 MiB in total (`EnvelopeLayout.MAX_SIZE`; writer and reader both enforce it). `readEnvelope` parses without decrypting (used for relay validation) and exposes the received header bytes as `header`; decryption uses those, never re-serialized ones.
- An envelope's identity is `envelopeHash(bytes)`: hex sha256 of the complete bytes (smep_rfc section 6). It is computed, never carried in the envelope; there is no uuid. Clients and relays dedup only on it, never on a header field, so nobody can post a different envelope first and get the real one skipped.
- `notifyTopic(identity, senderPkh, recipientPkh)` (`protocol/notify-topic.js`): the ntfy topic for one direction of a conversation, `"raven-"` + the first 32 hex digits of `sha256("smerp-ntfy-topic" ‖ X25519 shared secret ‖ recipient key)`. Only the two parties can derive it; `identity` must be one of them; a note to self has none. The test vector is in smerp_rfc section 7.
- `cryptoSupport()` (`crypto/support.js`) reports whether the runtime has the WebCrypto smep needs: `{ ok }` or `{ ok: false, reason: "no-webcrypto" | "no-x25519" }`. X25519 is the recent part (Firefox 130, Safari 17, Chromium 133), so it runs the real operations instead of checking that `crypto.subtle` exists.
- `insist(value, Class?)` from `smep/src/util/util.js` is the runtime type check used in constructors across both layers.

**smerp** is the reference messaging client built around untrusted relays that store opaque encrypted envelopes. It was rebuilt as independent modules glued together by the client: `sync/` (Scheduler) runs `session/` (RelaySession, one per relay), whose fetched batches go to `ingest/` (Ingestor), which writes storage. `client/` builds and wires them. Plain methods only: no `#private` methods in the new modules, and method names say concretely what they do.
- `client/smerp-client.js` (`SmerpClient`) holds the wiring: lifecycle, the sync interval (`setInterval`, outside the scheduler), the `EventBus`, and the public API. Dependencies are injected via constructor options with defaults (`TransportDefault`, `StorageMemory`, `Logger`, `RealClock`); `concurrency` is the scheduler's N. `debug: true` turns the default logger on; a given `logger` wins over it. `notify` (default `false`) makes `send()` push ntfy notifications; `ntfyUrl` (default `https://ntfy.sh`, http(s), trailing `/` stripped) is the client's ntfy server, for pushes and for subscribe links, so it matters with `notify` off too. Both are fixed for the client's lifetime: changing them means a new client.
- Public API: `start()`, `stop()`, `status`, `publicKeyHex`, `on(type, cb)` → unsubscribe, `sync()`, `send()`, `envelopesGet()`, `conversationsGet()`, `markRead(publicKeyHex)`, `renameConversation(publicKeyHex, name)`, `relaysGet()`, `relaysPut()`, `relaysDelete()`, `notifyTopic(publicKeyHex)` (the topic that peer pushes to us on, for the phone to subscribe to), and the `ntfyUrl` property. Every method except `on` throws `NotStartedError` unless `status === "running"` (async methods reject; `sync()` throws). The client does not expose the identity to UIs (the web UI passes it to its views itself); `client.identity` is still a property only because there are no private fields.
- Storage naming: `<resource>Get(options)` returns an array, `<resource>Put(record)` inserts or replaces by primary key and returns the key, `<resource>Delete(options)` returns a count. Resources: `envelopes` (key `hash`), `conversations` (key `publicKeyHex`), `relays` (key `relayUrl`). Network actions are plain verbs (`send`, `sync`).
- Events (`event/event-bus.js`, `EventTypes`) carry the stored record. The client maps module callbacks to them: Ingestor `onEnvelope`/`onConversation`/`onRejected` → `ENVELOPE`/`CONVERSATION`/`REJECTED`; a session save that changes a shown field, and `relaysPut`/`relaysDelete` → `RELAY` (`deleted`); a session save that raises `failureCount`, and a rejected scheduler step → `ERROR` (`relayUrl`); `sync()` → `SYNC` start/end; lifecycle → `STATUS`.
- **An envelope counts as sent only once a relay accepted it and it was downloaded back.** `send(recipientPkh, plaintext, { contentType })` (string or `Uint8Array`; envelopes over 4 MiB are refused by smep) encrypts once, calls `session.post(bytes)` on every enabled relay in parallel (`Promise.allSettled`), throws `DispatchError` if none accepted it, returns `{ hash, delivered, failed }`, starts a sync, and calls `pushNotification` without awaiting it. It stores nothing: every envelope, our own included, enters storage only through sync → Ingestor. Sends deliberately bypass the scheduler: they are one-off and user-driven, and want an answer now, not a queue position.
- **Notifications are pushed by the sender; relays never open outbound connections** (smerp_rfc section 7). `pushNotification(recipient)` POSTs `raven: new envelope received` (`Title`/`X-Sequence-ID: raven`) to `<ntfyUrl>/<notifyTopic>` through the injected transporter, only if `notify` is on, the recipient is not us, the conversation has `hasInbound` (a cold first contact never pushes) and no 429 pause is running (`ntfyPausedUntil`, Retry-After seconds, default 60 s). Best effort: 5 s timeout, no retry, never throws, never fails `send()`. No cooldown yet. The receiver's opt-in is subscribing to the topic in the ntfy app; the client stores nothing for it.
- **Relay changes stop and rebuild.** `relaysPut` / `relaysDelete` run through `changeRelays`: `await scheduler.stop()` (running steps finish and save), clear `sessions`, write storage, build sessions for enabled relays and a new scheduler, sync. Changes run one at a time on a promise chain. Because sessions only save during steps and posts, their saves cannot interleave with the user's relay writes; that is why there is no relay write lock. `saveRelayState` ignores a session that is no longer current and a relay that was deleted, so neither can write over a newer record or resurrect one. `relaysPut` keeps the stored sync fields (`cursor`, `relayPkh`, health) unless the caller sets them.
- `sync/scheduler.js` (`Scheduler`): runs whatever sessions the caller `add`s, at most `concurrency` steps at once. API: `add(session)`, `wake()`, `stop()` (not restartable; build a new one). Each session is in exactly one of three collections: `idle` (Set), `pending` (Set; insertion order = FIFO), `running` (Map session → step promise). N is `running.size`; `startDueSessions()` is the only place steps start, checks it before each start and has no `await`, so no lock is needed. After a step: `true` → back of `pending` (a backlog cannot starve others), `false` → `idle`. One timer, for the earliest pending session whose `notBefore()` has not passed. `wake()` moves idle sessions to pending and returns one shared promise (`whenDone`) resolved by `resolveIfDone()` when nothing is pending or running. That ends a round: each session gets at most `maxStepsPerRound` (50) steps per round (`stepsThisRound`, cleared when the round ends). A session that still has more after that goes idle (`onCapped`), and a `wake()` during the round skips it, so a hostile relay that always has more cannot keep `sync()` open. The scheduler knows nothing about HTTP, tokens, backoff or relay URLs.
- Session contract the scheduler relies on: `step()` → `Promise<boolean>` ("I have more to do"; a rejection counts as false and goes to `onError(error, session)`), and `notBefore()` = time of the next rate-limit token only. Longer waits (failure backoff, a 429's Retry-After) must not be in `notBefore()`: `step()` returns false without a request while they last. Otherwise a relay merely waiting for a token would be skipped by an explicit sync, or a relay backing off for an hour would hold a sync open.
- `session/relay-session.js` (`RelaySession`): one relay. Config (`relayUrl`, `relayToken`) is fixed for its lifetime (a relay change builds a new session). Owns cursor, `relayPkh`, health (`failureCount`, `lastSuccessAt`, `lastFailureAt`, `lastFailureReason`), its own `TokenBucket` (2/s, burst 3; starts full with every session) and `pausedUntil` (429, in memory). Takes `{ relay, identity, transporter, consume(frames), save(state), logger, clock }`. `step()`: decline while backing off (30 s doubling, 1 h cap) or paused → take a token (none: return true without a request) → `fetchBatch()` → `await save(state())`. `fetchBatch()` switches on the status: 200 with a valid cursor → `await consume(frames)`, then advance the cursor, success, true; broken framing with a valid cursor → consume the frames before the break, advance, failure, false; bad cursor → failure, cursor kept; 204 → success, false; 401 that taught a new relay key (`adoptRelayPkh` returns true) → success, true, so the next request is signed with it (no immediate retry, auth_rfc section 7); other 401 → failure with the relay's reason; 429 → `pauseForRetryAfter` (seconds only, default 5 s), false; anything else → failure. `consume` or `save` throwing rejects the step: the cursor stays and the relay is not blamed. A spec-compliant relay always returns a greater cursor, so there is no runaway cap. `post(bytes)` (sends): fails fast while paused, takes no token, does not touch health, saves a newly learned key, throws on anything but 200 ("relay key learned, send again" for a 401 with a new key).
- `session/request-builder.js` (`RequestBuilder`): builds complete signed requests in the shape `transporter.transport()` takes (`{ url, options: { method, headers, body? }, timeout }`); sends nothing. `buildGet(cursor, relayPkh)` and `buildPost(envelopeBytes, relayPkh)` are the only smerp requests. Holds `relayUrl`, `relayToken`, `identity`; the relay key is a parameter because the session owns it. Unsigned when `relayPkh` is null (first contact); adds `x-smerp-token` when there is a token; caches the HMAC key for one relay key and derives again when it changes. Uses the pure helpers of `auth/request-signer.js`.
- `ingest/ingestor.js` (`Ingestor`): the session's `consume`, shared by all sessions (`frames => ingestor.ingest(frames, relayUrl)`; `relayUrl` is only for rejection reports). Per frame in order: `envelopeHash` → skip if the hash is stored (before parsing or decrypting: most frames are duplicates from other relays) → `readEnvelope` → decrypt → `envelopesPut` → conversation update → callbacks. Parse/decrypt errors are rejections (skipped, `onRejected({ hash, reason, relayUrl })`, the batch goes on, the cursor moves past them); storage errors propagate so the session keeps its cursor and refetches (dedup makes that safe). **Tasks run one at a time** (`enqueue`, a promise chain): sessions ingest in parallel and every relay holds the same envelopes, so interleaving would announce and count an envelope twice or lose an unread increment. `markRead(publicKeyHex)` and `rename(publicKeyHex, name)` run on the same chain, so they cannot lose a concurrent increment (or the name) either. Don't remove this.
- Stored envelope: `{ hash, contentType, plaintext, senderPublicKeyHex, recipientPublicKeyHex, publicKeyHex (the peer), direction ("inbound" | "outbound"), sentAt (wire seconds × 1000), receivedAt (max(now, last + 1): strictly increasing, orders same-second envelopes) }`. There is no `read` field; unread state lives only in the conversation. Stored conversation: `{ publicKeyHex, unreadCount (envelopes addressed to us: inbound, plus notes to ourselves), lastMessageAt, hasInbound?, name? }`. `hasInbound: true` is set by the first inbound envelope from the peer (never by ours or a note to self) and gates notification pushes; conversations stored before it existed get it on the peer's next envelope. `name` is the user's local label for the peer (never sent), set only by `Ingestor.rename` (trimmed, at most `MAX_CONVERSATION_NAME` = 64 code points, empty removes it); everything else that writes a conversation copies the existing record, so the name survives.
- `protocol/` is the pure wire format, shared by the client and the mock relay: `SmerpHeaders`, `Status`, `MAX_ENVELOPE_BYTES` / `MAX_BATCH_BYTES` (4 MiB each), `MAX_RESPONSE_BYTES`, `encodeBatch` / `decodeBatch`, `parseCursor`. `GET /envelopes?cursor=N` returns a batch: `frame*`, `frame = uint32 BE length || envelope`, `x-smerp-cursor` = after the last envelope.
- Auth (spec: `smerp/src/auth/auth_rfc.txt`) is stateless and mandatory on every request. HMAC key = hash of the X25519 shared secret between signer and relay. `auth/request-signer.js` holds `canonicalRequest` (METHOD, target relative to the relay URL, timestamp, sha256(body)), `bodyHashHex`, `hmacKeyFor`, `normalizePkh`, `AuthHeaders`, and `RequestVerifier` (relay). Tests sign requests by hand with `RequestSigner` from `smerp/tests/helpers/request-signer.js`. Headers: `x-smerp-pkh`, `x-smerp-timestamp`, `x-smerp-signature`, and `x-smerp-token` for an access token (not `Authorization`: every smerp header is `x-smerp-*`); GET's mailbox is the signer. Every refusal is a 401 with optional free-text `x-smerp-unauthorized`, kept as `relay.lastFailureReason` (untrusted, display only).
- `log/logger.js` (`Logger`): developer logs, off by default (each call is then one boolean check), on with the client's `debug` flag. Each level (`debug`/`info`/`warn`/`error`) goes to the `console` method of the same name as `[smerp] HH:MM:SS.mmm message { fields }`. Contract, which any injected logger must meet: `level(message, fields?)` with a constant lowercase message and a plain object of cheap values, `child(fields)` (the client gives each session `child({ relayUrl })`), `enabled`. **Never log secrets or content**: no plaintext, private keys, relay tokens, signatures, HMAC keys or ntfy topics (nor ntfy URLs, which contain them); relay-supplied strings go in fields only. Failures the app must see are events, not log lines.
- `lib/`: generic building blocks. `TokenBucket` never waits (`tryTake`, `nextTokenAt`); `RealClock` (`now`, `sleep`, `timer(ms, fn)` → cancel). `ConcurrencyLimiter` is unused, kept on purpose; don't delete it.
- Pluggable backends follow documented interface contracts: `storage/storage-interface.js` (gets return arrays of detached copies; implementations `StorageMemory`, `indexeddb/`; a new backend should run the shared ordering and pagination suite `storageContract(test, () => new Storage())` from `smerp/tests/helpers/storage-contract.js`) and `transport/transport-interface.js` (`transport({ url, options, timeout, maxBytes })` → `{ status, headers, body: Uint8Array }`; `TransportDefault` never follows redirects (`redirect: "error"`, set after the caller's options), and streams the body, rejecting past `maxBytes`, which defaults to `MAX_RESPONSE_BYTES`: a full batch of the smallest envelopes with framing).
- `server/smerp-server.js` + `storage-server.js` + `http-helpers.js` are a **mock relay for development and tests only, never for production** (the warning heads `smerp-server.js`): in-memory append-only record store (`StorageServer`: `has`, `envelopesPut`, `envelopesGet({ pkh, after })`) on `node:http`, with a keypair generated per instance (or `privateKeyHex` option); `relayPkh()` returns it and `rotateKey()` replaces it. Routes are a `"METHOD /path"` table. It serves batched GETs (malformed cursor: 400), answers 200 without storing again for bytes it already holds (same `envelopeHash`), refuses POST bodies over 4 MiB with 400 (counted while streaming, so chunked bodies too), requires signed GET and POST (POST signer must be the envelope's sender or recipient) and, with the `tokens` option (a Set), an `x-smerp-token`. Every response carries `x-smerp-relay-pkh` and `Cache-Control: no-store`. `GET /dump` lists stored envelope metadata without auth (kept on purpose). `listen(port, host)` defaults to `127.0.0.1`; tests use `listen(0, "127.0.0.1")`.
- Tests live in `smerp/tests/{unit,integration,helpers}` (`node --test <dir>` recurses). There is one unit file per module, each using injected fakes. `integration/` covers `sync-pipeline` (Scheduler + RelaySession + Ingestor wired by hand), `client-e2e` (SmerpClients end to end against the mock relay on ephemeral ports) and `exports` (the package exports map, by self-reference). `helpers/fakes.js` has `VirtualClock` (timers fire only on `advance(ms)` / `drive(promise)`), `FakeRelays` (a scriptable transporter that logs requests and can announce a relay key per relay) and `tick`. `helpers/relay-fixtures.js` has `envelopeFor` (real smep envelopes), `startRelay`, `FakeSession`/`ScriptedSession` (scheduler doubles), `SlowStorage` (forces interleaving) and `RecordingLogger` (the logger contract; records `[level, message, fields]`). `helpers/storage-contract.js` is the shared storage suite. `helpers/request-signer.js` has `RequestSigner` (signs a raw request for the mock relay). Register cleanup with `t.after` so a failing test can't hang the run. With `VirtualClock`, wrap a client sync in `clock.drive(...)` when a session may have to wait for a token.

**webui** is a browser UI on top of `SmerpClient` (third layer: webui → smerp → smep). Vanilla DOM, no dependencies.
- `new WebUi({ privateKeyHex, root = document.body, storage?, recipientPublicKeyHex?, relays?, debug?, notify?, ntfyUrl? }).start()` first runs `browserSupport()` (`browser-support.js`: smep's `cryptoSupport()`, which runs the X25519 operations smep uses, plus a probe that IndexedDB opens when the default storage is used) and rejects with `UnsupportedBrowserError` (`reason`, a user-facing `message`) if the browser can't run it; then it derives the identity, creates the client with `IndexedDbStorage(publicKeyHex)` by default (passing `notify`, and `ntfyUrl` when given; there is no switch for them in the UI), adds each `relays` entry whose `relayUrl` is not already stored, opens the Send view prefilled when `recipientPublicKeyHex` is given, and mounts `AppShell`, adding the stylesheet as a `<style>` in `document.head`. `stop()` tears it all down. `deleteBrowserData()` (the Identity view's "Delete local data" card, via `shell.deleteBrowserData`) stops the client, so its database is closed, deletes every IndexedDB database of the origin with `deleteAllDatabases` (`browser-data.js`: `indexedDB.databases()`, else only our own database; a deletion another tab holds is reported as blocked, not awaited), and leaves a notice in place of the UI. The IndexedDB storage closes its connection on `versionchange`, so a delete in one tab is not blocked by another. The stylesheet's only source is `styles/webui.css.js` (`WEBUI_CSS`, a `String.raw` literal: no backticks or `${`), so the UI needs nothing served, imported or configured besides its JS, raw, bundled or from a CDN. There is no styling option: a different look means a different UI. There is one theme on purpose, no light/dark switch: a cool slate between light and dark (`color-scheme: dark`), so neither a light nor a dark page is a jarring jump; its text colors meet WCAG AA on every surface they sit on, so check contrast when changing a color token. The private key is never stored.
- `AppShell` (header, tab bar, active view) holds the UI's only `client.on` subscriptions and forwards each event to the active view. Views (`views/`) are constructed with `{ client, identity, shell, ... }` and implement `mount(container)`, `onEvent(event)`, `unmount()`; they never subscribe themselves. `identity` comes from `WebUi`, not the client (the Identity view needs it to reveal the private key). The thread view resets unread with `client.markRead` and renames in place in its header with `client.renameConversation`. Its header's "Notify" button (not for our own key) opens `openNotifyDialog` (`components/notify-dialog.js`) with `client.notifyTopic(peer)` and `client.ntfyUrl`: a `<dialog>` with an Android and an iPhone section, always both. Android gets a QR code of the `ntfy://` deep link (`notify-links.js`: `ntfyAppLink`, with `display` and, for an http server, `secure=false`) and an "Open in ntfy" link; iPhone (the iOS app has no subscribe link) gets a QR code of the plain topic. Each has the topic in a read-only field with `copyButton` (`components/copy-button.js`, shared with the Identity view). QR codes come from `qr.js` (`qrMatrix(text)`: byte mode, level M, versions 1 to 40, lowest-penalty mask; DOM-free) drawn on a canvas by `components/qr-code.js`, black on white whatever the theme. A peer is shown by `peerLabel()` (`format.js`): its name, "Note to self" for our own key, else the short hex. Chat rows and the thread header add `avatar()` (`components/avatar.js`): the label's first character or the key's first two hex digits, colored by `peerHue(publicKeyHex)`. Reusable pieces live in `components/`.
- Peer content is untrusted: build DOM only with `h()` from `dom.js` (text nodes), never `innerHTML`.
- Display is text vs file only: `TEXT_UTF8` renders as text; any other content type gets a download button. Envelopes carry no filename or MIME type, so `file-type.js` guesses the extension from the file's leading bytes (no extension if unknown). Sending a file uses `ContentTypes.FILE`.
- Tests (`webui/tests/{unit,helpers}`) cover only the DOM-free modules (`format.js`, `file-type.js`, `browser-support.js`, `browser-data.js`, `notify-links.js`, `qr.js`), `WebUi` option checks (with a stub `HTMLElement`) and the client API contract; nothing renders DOM in tests. `helpers/fake-client.js` (`FakeClient`) is the public client API backed by a `StorageMemory`; it logs calls and `emit`s events. `unit/client-api.test.js` fails when the webui uses a client member that `SmerpClient` lacks, or when the fake offers one, so client API changes surface there first.
- `qr.js` is checked against the ISO 18004 worked example and tables, and against matrices from segno 1.6.1 (`helpers/qr-fixtures.js`, generated outside the repo; segno pads a whole zero byte when the bit stream is already byte-aligned, which the spec doesn't, so that function was patched for the fixtures).
- Demo: run the mock relay, `python3 -m http.server 8080` from the repo root, open `http://localhost:8080/webui/demo/` (add `?debug` for client logs in the console, `?notify` to push ntfy notifications, `?ntfy=<url>` for another ntfy server). No relay key is needed; the client learns it.
