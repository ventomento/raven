SMERP: Secure Messaging Envelope Relay Protocol, Version 1

1. Overview
===========

SMERP moves SMEP envelopes (docs/smep_rfc.txt) between clients and relay
servers over HTTP(S). A client uploads an envelope to its relays. The
relays forward it through the federation of relays they know. The
recipient downloads it from whichever relays it uses. Delivery is
best-effort, and no relay is trusted or authoritative.

Every request is signed as specified in docs/auth_rfc.txt.
Every response carries the relay's current public key in
x-smerp-relay-pkh, so a relay is configured by URL and type only.

Every response MUST carry:

    Access-Control-Allow-Origin: *
    Access-Control-Expose-Headers: *

That is all the CORS a relay needs, and it is what lets a browser client
read responses from any relay. Requests carry no custom header and no
Content-Type, so a browser sends them without a preflight and a relay
needs no OPTIONS route. Clients authenticate by signature, never by
cookies, so a preflight would protect nothing.

Responses use these status codes only:

    200   success, with a body
    204   success, nothing to return
    400   malformed request
    401   refused, see below
    429   throttled, see below

Refusal. A relay MAY refuse any request, for any reason. It MUST answer
a refusal with 401, so the client can handle it. It MAY put a reason in
x-smerp-unauthorized, but need not (auth_rfc section 8). Who may use a
relay, and how an operator controls that, is outside this protocol.

Throttling. A relay MAY throttle any request, for any reason and by any
measure it chooses (requests, bytes, per signer). Its limits are relay
policy and are not advertised. It MUST answer a throttled request with
429 and Retry-After.

A 429 MUST carry Retry-After as a non-negative integer number of
seconds, counted from the response. Any other form, or no header, is
a relay bug. A long wait is legitimate.

A 429 covers the client's upload and download on that relay, whichever
request caused it. It is not a relay failure: a client SHOULD NOT count
it as one.


2. Relay Types
==============

archive
    Stores every accepted envelope indefinitely.

relay
    Makes no retention promise. It may delete an envelope at any time.

    As a guideline, a relay SHOULD keep an envelope until either:

    - it has been served by GET to its recipient, that is, to a request
      signed by the envelope's recipient_public_key, or
    - a retention time has passed since it was accepted. 7 days is
      RECOMMENDED.

    Serving an envelope to its sender is not delivery. Clients also
    download their own sent envelopes (section 4), usually right after
    sending, so a relay that deletes on any GET would often delete an
    envelope before its recipient could fetch it.

The client configures the type for each relay. The protocol does not
advertise it. Neither type guarantees delivery.


3. Upload
=========

    POST /envelopes?pkh=<pkh>&ts=<timestamp>&sig=<signature>
    Body: one SMEP envelope

Signed; the signature covers the envelope bytes. The client sends no
Content-Type, and a relay MUST NOT require one: the endpoint defines the
body. Which signers the
relay accepts is its policy. A relay typically accepts the envelope's
sender (a client sending) or recipient (a client keeping a copy, e.g.
on an archive), and the peer relays it federates with (section 5).

    200   accepted, including an envelope already held (same hash,
          smep_rfc section 6)
    400   the body is not a valid envelope, or it is larger than 4 MiB
          (smep_rfc section 4). A relay MAY reject on Content-Length
          before reading the body.
    401   refused
    429   throttled

The client posts to all of its relays. The send succeeds if at least
one relay returns 200.


4. Download
===========

    GET /envelopes?cursor=<cursor>&pkh=<pkh>&ts=<timestamp>&sig=<signature>

Signed. The mailbox is the signer's: the relay returns the envelopes
after cursor whose sender or recipient is the signer pkh, so clients
also receive their own sent envelopes.

    200   body: a batch of one or more envelopes (below)
          x-smerp-cursor: <cursor after the last envelope in the batch>
          x-smerp-epoch: <epoch>
    204   no envelope after cursor
          x-smerp-epoch: <epoch>
    401   refused
    429   throttled

A batch packs as many envelopes as fit in one response, so many small
envelopes are fetched with one request:

    Content-Type: application/octet-stream
    body  = frame *frame
    frame = length envelope
    length: uint32, big-endian, the byte length of envelope

The relay puts the envelopes in cursor order, starting with the first
one after cursor. It adds envelopes while the sum of their lengths
stays at most 4 MiB (4,194,304 bytes), framing not counted. A batch
always holds at least one envelope; since an envelope is at most 4 MiB
(smep_rfc section 4), the first always fits. A relay SHOULD fill the
batch as far as it can.

The length prefix delimits each envelope, so a client can skip one
envelope that fails to parse and still read the rest of the batch.

The cursor is a non-negative integer defined by the relay. It starts at
0, and each 200 MUST return a cursor greater than the one requested,
even after the relay deletes envelopes. The client stores a cursor per
relay. It advances the cursor to x-smerp-cursor only once it has
processed every envelope in the batch, and repeats the request until it
gets 204.

A cursor that is missing, not an integer, or not greater than the
requested one is a relay failure; the client keeps its cursor.

The epoch names the relay's cursor space: an opaque string of 1 to 64
characters from A-Z, a-z, 0-9, "-" and "_". Every response to GET
/envelopes MUST carry it; a relay MAY send it on every response.

- A relay MUST change its epoch whenever its cursors could start over
  or go backwards: its storage was wiped, restored from an older
  backup, or replaced (for example a new server under the same URL).
  Without that, a client would keep a cursor beyond every envelope the
  relay now holds and silently miss envelopes until the new cursors
  passed it.
- A relay MUST NOT change its epoch otherwise: every client then
  fetches its whole mailbox again.
- So a relay that keeps envelopes only in memory needs a new epoch on
  every start, and a relay with persistent storage stores its epoch
  with the envelopes. A random value made when the storage is created
  does both.

The client stores the epoch per relay, with the cursor. A response
whose epoch differs from the stored one answered a cursor that no
longer means anything: the client ignores it, sets its cursor to 0,
stores the new epoch and fetches again. That is not a relay failure.
Deduplication by envelope hash (section 6) makes the refetch safe. The
first epoch a client sees is just stored. An epoch that is missing or
malformed changes nothing; a relay that sends none gives its clients no
way to notice a reset.

A body whose framing is broken (a length that runs past the end of the
body, a trailing partial length, or no frame at all) is a relay
failure. If the cursor is valid, the client processes the frames before
the break and advances the cursor, so a broken batch cannot stall the
mailbox.


5. Federation
=============

Both relay types SHOULD forward each newly accepted envelope to the peer
relays they know, using POST /envelopes. An envelope whose hash the
relay already holds is not forwarded again, which ends loops. The hash
is the SHA-256 of the envelope bytes (smep_rfc section 6); a relay
MUST NOT treat an envelope as held because a header field matches,
or anyone could post a different envelope first and have the real one
dropped.

A forwarding relay signs with its own keypair and learns each peer's
key like any client does. Which peers a relay forwards to, and which
peers it accepts envelopes from, is local policy. A forwarded envelope
carries no proof of its sender: the signature identifies the
forwarding relay, not the envelope's author.

A relay that deletes an envelope SHOULD keep its hash for a while
longer, so that a copy arriving again from a peer is recognized and
neither stored nor forwarded again.

Envelopes MUST be stored and forwarded byte-identical.


6. Client Rules
===============

- Deduplicate by envelope hash (smep_rfc section 6): the same envelope
  arrives from many relays.
- Drop an envelope that fails to parse or decrypt, and advance the
  cursor past it. Only a local failure (storage) keeps the cursor, so
  the batch is fetched again later.
- Do not create or upload an envelope larger than 4 MiB.
- Store each relay's epoch with its cursor. When a response carries a
  different epoch, ignore that response and fetch again from cursor 0
  (section 4).
- On 429, wait for Retry-After (seconds) before contacting
  that relay again (section 1). A client SHOULD remember the wait
  across restarts, and MAY cap it, so a bad value cannot block a relay
  for long. A missing or malformed Retry-After still means wait: the
  client picks a short default.
- Sign every request and learn the relay key from x-smerp-relay-pkh; a
  401 that taught a new key is not a failure, and the next request is
  signed with it (auth_rfc sections 5 and 7).
- Treat any other 401 as a failed request to that relay.
  The x-smerp-unauthorized reason, if any, is display text only.
- Do not follow redirects: a 3xx is a failed request to that relay,
  since following it would send the signed request elsewhere.
- Send no custom request header and no Content-Type, so a browser needs
  no preflight (section 1). A browser client SHOULD also ask not to
  cache responses (fetch's cache: "no-store"): batches have no use once
  processed, and need not stay on disk.
- Do not log a request URL: it holds the signature (auth_rfc section 9).
- Do not read a response body larger than the largest valid batch
  (4 MiB of envelopes plus their 4-byte lengths); a larger one is a
  failed request.
- A client MAY limit the requests to one relay per sync, so a relay
  that always returns more cannot keep a sync from ending. The rest
  of the backlog is fetched by the next sync.


7. Client Notifications (optional)
==================================

A sending client MAY push a phone notification through ntfy
(https://ntfy.sh) when it sends. Relays take no part: they never open
an outbound connection. The receiver opts in per conversation by
subscribing to the topic below in the ntfy app.

Topic. One per direction of a conversation, which only the two parties
can derive:

    shared = X25519(own private key, peer public key)
    topic  = "raven-" || hex(SHA-256("smerp-ntfy-topic" || shared ||
                                     recipient public key))[0..32]

The label is the 16 ASCII bytes "smerp-ntfy-topic", the recipient key is
its 32 raw bytes, and the result is the first 32 lowercase hex digits.
There is no topic for a note to self.

Test vector (private keys are the 32-byte scalars, before clamping):

    alice private  4040404040404040404040404040404040404040404040404040404040404041
    alice public   16cc47ba4376ea9de41e2e0d41d924292b54c74b2a9b76201b3aa51a6906654e
    bob private    5050505050505050505050505050505050505050505050505050505050505051
    bob public     f55fc0309085dc04138f57894ebd864fae33581c7c7a0bf4bd5bd2790a172165
    alice -> bob   raven-7393d61a4b43bc37bd434fd736f061f4
    bob -> alice   raven-21c3bb9c242c2d5ee31685d3a910898c

Push:

    POST <ntfy server>/<topic>
    Title: raven
    X-Sequence-ID: raven

    New message

or, when several messages are reported, with the body

    <N> new messages

The body says only how many messages arrived: no sender, hash or
content. X-Sequence-ID lets ntfy clients replace the previous
notification of the topic instead of stacking a new one, so N counts
every message of the burst so far, not only those since the last push.

Rules for a client that pushes:

- Push only when the user turned it on; it is off by default.
- Push only after at least one relay accepted the envelope.
- Count an envelope once, however many relays accepted it.
- Never push for a note to self.
- Push only to a peer it has received an envelope from, so a first
  message to a stranger never pushes.
- Push to its own configured ntfy server, never to one a peer names: a
  peer-chosen server would learn the sender's IP address.
- Treat the push as best effort: a short timeout, no retry, and never
  fail or delay the send because of it. On 429, wait for Retry-After
  (seconds) before pushing again.
- Never log the topic.
- SHOULD batch pushes per peer, so an active conversation does not
  notify on every message. The reference client pushes the first
  message of a burst at once and opens a 3 minute window. Messages sent
  during a window are counted, and when it ends one push reports the
  burst's total and opens the next window. A window that ends with
  nothing counted ends the burst. State is in memory only: closing the
  client may lose a count that was not pushed yet.

Both peers must use the same ntfy server for a push to reach the
subscriber; the default is https://ntfy.sh. A topic reveals only when
one peer sends to the other and how many messages were sent, but the
ntfy server sees the sender's IP address publishing to it and the
subscriber's phone receiving it.


8. Security Notes
=================

- Relays see sender, recipient, timestamp, size and timing.
- Uploads are signed, but anyone can create an identity, so a relay
  that accepts any sender still lets anyone post to any recipient.
  Limiting that is relay policy: rate limits, accepted signers.
- A relay can verify who uploaded an envelope, not who wrote it once it
  has been forwarded (section 5).
- Relays can drop, delay or withhold envelopes. Use several relays.
