SMERP: Secure Messaging Envelope Relay Protocol, Version 1

1. Overview
===========

SMERP moves SMEP envelopes (smep/smep_rfc.txt) between clients and relay
servers over HTTP(S). A client uploads an envelope to its relays. The
relays forward it through the federation of relays they know. The
recipient downloads it from whichever relays it uses. Delivery is
best-effort, and no relay is trusted or authoritative.

Every request is signed as specified in smerp/src/auth/auth_rfc.txt.
Every response carries the relay's current public key in
x-smerp-relay-pkh, so a relay is configured by URL and type only, plus
an access token if its operator requires one.

Responses use these status codes only:

    200   success, with a body
    204   success, nothing to return
    400   malformed request
    401   refused: authentication or relay policy (auth_rfc section 9)
    429   throttled, see section 6


2. Relay Types
==============

archive
    Stores every accepted envelope indefinitely.

relay
    Makes no retention promise. It may delete an envelope at any time.

    As a guideline, a relay SHOULD keep an envelope until either:

    - it has been served by GET to its recipient, that is, to a request
      signed by the envelope's recipient_public_key, or
    - a retention time has passed since it was accepted. 7 days is
      RECOMMENDED.

    Serving an envelope to its sender is not delivery. Clients also
    download their own sent envelopes (section 4), usually right after
    sending, so a relay that deletes on any GET would often delete an
    envelope before its recipient could fetch it.

The client configures the type for each relay. The protocol does not
advertise it. Neither type guarantees delivery.


3. Upload
=========

    POST /envelopes
    Content-Type: application/octet-stream
    Body: one SMEP envelope

Signed; the signature covers the envelope bytes. Which signers the
relay accepts is its policy. A relay typically accepts the envelope's
sender (a client sending) or recipient (a client keeping a copy, e.g.
on an archive), and the peer relays it federates with (section 5).

    200   accepted, including an envelope already held (same hash,
          smep_rfc section 6)
    400   wrong Content-Type, the body is not a valid envelope, or it
          is larger than 4 MiB (smep_rfc section 4). A relay MAY reject
          on Content-Length before reading the body.
    401   refused
    429   throttled

The client posts to all of its relays. The send succeeds if at least
one relay returns 200.


4. Download
===========

    GET /envelopes?cursor=<cursor>

Signed. The mailbox is the signer's: the relay returns the envelopes
after cursor whose sender or recipient is the signer pkh, so clients
also receive their own sent envelopes.

    200   body: a batch of one or more envelopes (below)
          x-smerp-cursor: <cursor after the last envelope in the batch>
    204   no envelope after cursor
    401   refused
    429   throttled

A batch packs as many envelopes as fit in one response, so many small
envelopes are fetched with one request:

    Content-Type: application/octet-stream
    body  = frame *frame
    frame = length envelope
    length: uint32, big-endian, the byte length of envelope

The relay puts the envelopes in cursor order, starting with the first
one after cursor. It adds envelopes while the sum of their lengths
stays at most 4 MiB (4,194,304 bytes), framing not counted. A batch
always holds at least one envelope; since an envelope is at most 4 MiB
(smep_rfc section 4), the first always fits. A relay SHOULD fill the
batch as far as it can.

The length prefix delimits each envelope, so a client can skip one
envelope that fails to parse and still read the rest of the batch.

The cursor is a non-negative integer defined by the relay. It starts at
0, and each 200 MUST return a cursor greater than the one requested,
even after the relay deletes envelopes. The client stores a cursor per
relay. It advances the cursor to x-smerp-cursor only once it has
processed every envelope in the batch, and repeats the request until it
gets 204.

A cursor that is missing, not an integer, or not greater than the
requested one is a relay failure; the client keeps its cursor.

A body whose framing is broken (a length that runs past the end of the
body, a trailing partial length, or no frame at all) is a relay
failure. If the cursor is valid, the client processes the frames before
the break and advances the cursor, so a broken batch cannot stall the
mailbox.

Relays that serve browser clients MUST expose x-smerp-cursor via CORS,
in addition to the headers listed in auth_rfc section 9.


5. Federation
=============

Both relay types SHOULD forward each newly accepted envelope to the peer
relays they know, using POST /envelopes. An envelope whose hash the
relay already holds is not forwarded again, which ends loops. The hash
is the SHA-256 of the envelope bytes (smep_rfc section 6); a relay
MUST NOT treat an envelope as held because a header field matches,
or anyone could post a different envelope first and have the real one
dropped.

A forwarding relay signs with its own keypair and learns each peer's
key like any client does. Which peers a relay forwards to, and which
peers it accepts envelopes from, is local policy. A forwarded envelope
carries no proof of its sender: the signature identifies the
forwarding relay, not the envelope's author.

A relay that deletes an envelope SHOULD keep its hash for a while
longer, so that a copy arriving again from a peer is recognized and
neither stored nor forwarded again.

Envelopes MUST be stored and forwarded byte-identical.


6. Client Rules
===============

- Deduplicate by envelope hash (smep_rfc section 6): the same envelope
  arrives from many relays.
- Drop an envelope that fails to parse or decrypt, and advance the
  cursor past it. Only a local failure (storage) keeps the cursor, so
  the batch is fetched again later.
- Do not create or upload an envelope larger than 4 MiB.
- On 429, wait for Retry-After (seconds) before contacting
  that relay again.
- Sign every request and learn the relay key from x-smerp-relay-pkh; a
  401 that taught a new key is not a failure, and the next request is
  signed with it (auth_rfc sections 5 and 7).
- Send a relay's access token, if configured, on every request to that
  relay only (auth_rfc section 8).
- Treat any other 401 as a failed request to that relay.
  The x-smerp-unauthorized reason, if any, is display text only.
- Do not follow redirects: a 3xx is a failed request to that relay,
  since following it would send the signed request and the access
  token elsewhere.
- Do not read a response body larger than the largest valid batch
  (4 MiB of envelopes plus their 4-byte lengths); a larger one is a
  failed request.
- A client MAY limit the requests to one relay per sync, so a relay
  that always returns more cannot keep a sync from ending. The rest
  of the backlog is fetched by the next sync.


7. Security Notes
=================

- Relays see sender, recipient, timestamp, size and timing.
- Uploads are signed, but anyone can create an identity, so a relay
  that accepts any sender still lets anyone post to any recipient.
  Limiting that is relay policy: rate limits, accepted signers, access
  tokens.
- A relay can verify who uploaded an envelope, not who wrote it once it
  has been forwarded (section 5).
- Relays can drop, delay or withhold envelopes. Use several relays.
