SMERP Authentication Protocol v1

1. Overview
===========

SMERP Authentication provides proof-of-possession of a client's long-term
X25519 private key.

The client and relay each hold an X25519 keypair. Authentication is performed
by deriving a shared secret and creating an HMAC signature over a timestamp.

The protocol is stateless and consists of a single HTTP request.

Usage:

    GET /envelopes?pkh=<client_pkh>&cursor=<cursor>

Only GET /envelopes is authenticated. POST /envelopes carries an opaque
encrypted envelope and requires no authentication.


2. Terminology
==============

Client
    Entity requesting authentication.

Relay
    Entity verifying authentication.

PKH
    Hex-encoded 32-byte X25519 public key (64 hex characters).
    Implementations MUST accept an optional "0x" prefix and hex digits
    in either case.

Timestamp
    Unix timestamp in seconds encoded as a decimal UTF-8 string.

Signature
    Hex-encoded HMAC-SHA256 output.


3. Cryptographic Primitives
===========================

Shared secret:

    shared_secret =
        X25519(
            private_key,
            public_key
        )

An all-zero shared_secret (produced by a low-order public key) MUST be
rejected.

Proof key:

    proof_key =
        SHA256(shared_secret)

Signature:

    signature =
        HMAC-SHA256(
            proof_key,
            UTF8(timestamp)
        )

All cryptographic operations use raw bytes.
Hex encoding is only used for transport.

The proof key is derived without domain separation: it is the same
SHA256(shared_secret) that SMEP uses as the AES-GCM key for envelopes
between the same two keypairs.


4. Timestamp Rules
==================

The timestamp MUST:

- be a Unix timestamp in seconds
- be represented as a base-10 decimal string
- contain no leading zeros
- be encoded as UTF-8 before signing


Example:

    1750201234


The relay defines the accepted clock-skew window.
Requests outside this window MUST be rejected.

The relay signs the x-smerp-timestamp header value exactly as received.
It need not enforce the formatting rules above: a timestamp formatted
differently from what the client signed fails verification.

The reference relay accepts timestamps within 300 seconds of its clock,
in either direction.


5. Client Authentication
========================

The client computes:

    shared_secret =
        X25519(
            client_private_key,
            relay_public_key
        )


    proof_key =
        SHA256(shared_secret)


    signature =
        HMAC-SHA256(
            proof_key,
            UTF8(timestamp)
        )


The client sends:

    GET /envelopes?pkh=<client_pkh>&cursor=<cursor>


Query parameters:

    pkh
        The client's own public key hex. It identifies both the
        mailbox being read and the key the relay verifies against.

    cursor
        Paging position. Not part of authentication.


Headers:

    x-smerp-timestamp: <timestamp>
    x-smerp-signature: <signature_hex>


Requirements:

    x-smerp-timestamp
        MUST contain the signed timestamp.

    x-smerp-signature
        MUST contain lowercase hexadecimal encoding of
        the HMAC-SHA256 output.


The proof key depends only on the two keypairs, so the client MAY derive
it once per relay and reuse it.


6. Relay Verification
=====================

The relay extracts:

    pkh        (client public key hex, from the pkh query parameter)
    timestamp  (x-smerp-timestamp header)
    signature  (x-smerp-signature header)


If any of these is missing, authentication fails.


The relay MUST:


1. Validate the timestamp.

   The timestamp MUST parse as an integer.
   Requests outside the accepted clock-skew window MUST be rejected.


2. Compute:

    shared_secret =
        X25519(
            relay_private_key,
            client_pkh
        )


    proof_key =
        SHA256(shared_secret)


    expected_signature =
        HMAC-SHA256(
            proof_key,
            UTF8(timestamp)
        )


3. Compare:

    expected_signature

against:

    received_signature


The comparison MUST use a constant-time comparison function.


If the signatures match, authentication succeeds.
Otherwise authentication fails.


On failure the relay responds:

    401 Unauthorized
    x-smerp-unauthorized: <reason>

The client treats any 401 as an authentication failure for that relay.


7. Security Properties
======================

Provides:

- Proof-of-possession of the client's X25519 private key.
- Stateless relay verification.
- Replay resistance bounded by the timestamp acceptance window.


Does not provide:

- Single-use authentication proofs.
- Protection against replay within the accepted timestamp window.
- Forward secrecy for authentication requests.
- Request binding. The signature covers only the timestamp, not the
  method, path, pkh or cursor. A captured request can be replayed within
  the window with any cursor. The pkh is bound only implicitly: the proof
  key is specific to the client-relay key pair.


TLS SHOULD be used for transport protection.
